# warehouse_bringup

Top-level launch files and configuration. This is the entry point for running the system: every
demo starts with `ros2 launch warehouse_bringup ...`.

## Files

| File | What it does |
|---|---|
| `launch/sim.launch.py` | Everything for one simulated robot: Gazebo (world scope, `hardware:=gz` only), the robot (`robot.launch.py`) at its spawn pose ([Where the robot spawns](#where-the-robot-spawns)) and RViz. Sets `use_sim_time` for every node with `SetParameter`. RViz runs in the robot's absolute namespace with the same `/tf` remaps as the robot |
| `launch/robot.launch.py` | The robot scope (plan §2.3), inside `PushROSNamespace(/<namespace>)` with `/tf` and `/tf_static` remapped to the namespace: `robot_state_publisher`, the controller manager (in Gazebo, or `ros2_control_node` for mock hardware), the three controller spawners and the EKF. Sets `use_sim_time` for its own nodes, so it also runs on its own. The namespace is absolute because the gz topic names in the URDF are: an enclosing namespace must not move the ROS side away from them. Phase 9 includes it once per robot |
| `rviz/robot.rviz` | RViz view of one robot: model, TF, scan (best effort), EKF and wheel odometry. Topic names are relative, so they resolve in the namespace RViz runs in. The TF display starts with the frames of the visual-only parts hidden (shell, bumpers, tote tray, stop button, status light, lidar mount, wheel hubs); tick them under TF > Frames |

## Running

From the workspace root, after `colcon build` and `source install/setup.bash`:

```bash
# Gazebo window + RViz, robot in /robot1 (the defaults)
ros2 launch warehouse_bringup sim.launch.py world:=empty namespace:=robot1

# The warehouse, generated from warehouse_layout's layout.yaml; robot1 spawns at its spawn pose
ros2 launch warehouse_bringup sim.launch.py world:=warehouse

# No windows at all (SSH, tests); the scanner still renders through EGL
ros2 launch warehouse_bringup sim.launch.py headless:=true

# No simulator: mock hardware, wall clock. What CI tests
ros2 launch warehouse_bringup sim.launch.py hardware:=mock

# World and robot separately, as Phase 9 will do once per robot (two terminals)
ros2 launch warehouse_gazebo gazebo.launch.py headless:=true
ros2 launch warehouse_bringup robot.launch.py namespace:=robot1
```

In the warehouse, RViz (fixed frame `odom`) shows the scan outlining the walls and the shelf
plinths.

`robot.launch.py` takes the same `namespace`, `hardware`, `use_sim_time`, `x`, `y` and `yaw`
arguments as `sim.launch.py` (table below); it does not start Gazebo or RViz. It does not know
the world either, so it does not read the registry: its `x`, `y` and `yaw` default to `0.0`.

| Argument | Default | Meaning |
|---|---|---|
| `world` | `empty` | World file in `warehouse_gazebo/worlds`: `empty` (ground plane) or `warehouse` (generated by `warehouse_layout`) |
| `namespace` | `robot1` | Robot namespace: nodes, topics, TF and gz topics live under it. `namespace:=/` runs the robot without one (`ros2 launch` refuses an empty value) |
| `hardware` | `gz` | `gz` (Gazebo through `gz_ros2_control`) or `mock` (`mock_components`). `real` is reserved and refused |
| `use_sim_time` | `true` for `gz`, `false` for `mock` | Use Gazebo's `/clock` |
| `headless` | `false` | No Gazebo window and no RViz |
| `rviz` | `true` | Start RViz (never when headless) |
| `x`, `y`, `yaw` | empty | Spawn pose in the world, in m and rad (`gz` only). Each one not given comes from the location registry, or is 0: [Where the robot spawns](#where-the-robot-spawns) |

## Where the robot spawns

`sim.launch.py` works out the spawn pose before anything starts, one value at a time:

1. `x`, `y` or `yaw` given on the command line: that value.
2. Otherwise, if the location registry `warehouse_layout/generated/locations.yaml` was
   generated for this world (its `world:` key), the value from the robot's spawn pose there:
   the entry with `kind: spawn` and `robot:` equal to the namespace. robot1 spawns at the world
   origin facing east (+x); robot2 and robot3 park 1.2 m to its south and north.
3. Otherwise (the `empty` world): 0.

It logs the result:

```text
[INFO] [launch.user]: /robot1 spawns at x 0 m, y 0 m, yaw 0 rad (its registry pose spawn_robot1)
```

In the warehouse, a namespace with no spawn pose in the registry stops the launch before
Gazebo starts, with an error that lists the namespaces it has. Give `x`, `y` and `yaw`, or add
a spawn to `layout.yaml` and run `ros2 run warehouse_layout generate`.

**Why the registry pose goes to Gazebo unchanged.** The layout and the registry are written in
the map frame, and the map frame is the Gazebo world frame, with its origin at robot1's spawn
pose (warehouse_layout README). The EKF starts `odom` where the robot spawns, so for robot1
`odom`, `map` and the world are the same frame at the start, and a map made from there lines up
with the world. A layout fit test keeps robot1 at (0, 0, 0).

**Why an `OpaqueFunction`.** A launch argument's default can be a substitution
(`use_sim_time`'s is "is `hardware` equal to `gz`"), but this one needs Python: read a file from
another package's share directory, then look up the namespace in it. An `OpaqueFunction` is a
Python function that launch calls once every argument has its value; it returns more actions.
Here it returns `SetLaunchConfiguration` actions that fill in `x`, `y` and `yaw`. It runs
first, before Gazebo: an error raised while `gz sim` is starting would leave the Gazebo server
running after the launch has stopped.

Check where the robot is (ground truth, the world pose, `frame_id` `map`):

```bash
ros2 topic echo /robot1/ground_truth/odom --once --field pose.pose.position   # about 0, 0
```

## Driving with teleop

```bash
ros2 run teleop_twist_keyboard teleop_twist_keyboard \
  --ros-args -r __ns:=/robot1 -p stamped:=true -p use_sim_time:=true
```

- `-r __ns:=/robot1` puts teleop in the robot's namespace, so it publishes `/robot1/cmd_vel`.
- `stamped:=true`: Jazzy's `diff_drive_controller` 4.42 accepts only `TwistStamped`.
- `use_sim_time:=true` (Gazebo only; leave it out for `hardware:=mock`): the controller computes
  the age of a command from its header stamp and brakes once the newest command is older than
  `cmd_vel_timeout` (0.15 s). A wall-clock stamp is decades ahead of sim time, never looks old,
  and the robot keeps driving after you release the key (plan R1).

teleop publishes one command per key event and nothing when you release a key, so each command
drives the robot for 0.15 s before it brakes. Measured in Gazebo on 2026-11-06, at teleop's
0.5 m/s and 1.0 rad/s:

- **Tap** a key for a small, precise move: `j` turns the robot about 4°, `i` moves it about
  1.4 cm, and it stands still within about 0.3 s of the key press.
- **Hold** a key to drive. After you release it, the robot stands still about 0.5 s later:
  0.15 s until the timeout, then 0.33 s of braking from full teleop speed. A held key starts
  with a short stop (see [below](#things-that-look-wrong-but-are-not)).

The hard limits (1.2 m/s forward, 0.3 m/s reverse, 2 rad/s) apply whatever teleop asks for.

## Checking the robot by hand

```bash
ros2 control list_controllers -c /robot1/controller_manager    # three controllers, all active
ros2 topic info -v /robot1/cmd_vel     # TwistStamped, diff_drive_controller the only subscriber
ros2 topic info -v /robot1/tf          # publishers: robot_state_publisher and ekf_filter_node
ros2 topic echo /robot1/odom/wheel --field child_frame_id      # base_footprint, no prefix
ros2 topic hz /robot1/scan             # 10 Hz (when Gazebo runs at real time)
# TF tools listen on /tf, so remap them to the robot's tree:
ros2 run tf2_tools view_frames --ros-args -r /tf:=/robot1/tf -r /tf_static:=/robot1/tf_static
ros2 run rqt_tf_tree rqt_tf_tree --ros-args -r /tf:=/robot1/tf -r /tf_static:=/robot1/tf_static
```

## Things that look wrong but are not

- `diff_drive_controller` logs `Velocity command timed out. Braking.` once per second whenever
  no command is arriving, including at rest. That is `cmd_vel_timeout` at work.
- A held teleop key moves the robot a little, stops it for 0.2-0.3 s, then drives on smoothly.
  The desktop repeats a held key only after a delay (GNOME: 500 ms, then every 30 ms), teleop
  sends nothing in that gap, and `cmd_vel_timeout` (0.15 s) brakes the robot until the repeats
  arrive. Taps are not affected.
- `ros2 topic info /tf` shows one publisher, `diff_drive_controller`, which never sends anything:
  the controller always creates its `/tf` publisher and only `enable_odom_tf: false` keeps it
  quiet. The controller manager runs inside Gazebo (or, for mock hardware, outside the `/tf`
  remaps, which it would otherwise pass on to every controller), so that publisher stays on the
  global `/tf`.
- `Could not enable FIFO RT scheduling policy` from the controller manager: a normal desktop
  user may not use real-time scheduling. Simulation does not need it.

## Prerequisites

`rosdep install --from-paths src --ignore-src -y` installs everything this package names,
including the tools above (`teleop_twist_keyboard`, `rqt_tf_tree`, `tf2_tools`, `ros2controlcli`).
